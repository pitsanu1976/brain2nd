## Clause 1 Scope (p.1-2)

- มาตรฐานวางพื้นฐานการเก็บข้อมูล reliability and maintenance (RM) ในรูปแบบมาตรฐาน สำหรับอุปกรณ์ทุกประเภทในอุตสาหกรรม petroleum, natural gas, petrochemical ตลอด operational life cycle (ISO 14224 cl. 1, p.1)
- วางตัวเองเป็น "ภาษากลางด้าน reliability" และรายการ failure mode ในส่วน normative ใช้เป็นเหมือน "thesaurus" สำหรับงานวิเคราะห์ทั้งเชิงปริมาณและคุณภาพ (cl. 1, p.1)
- กำหนดข้อกำหนดที่ระบบ RM data (in-house หรือ commercial) ต้องมีถ้าออกแบบเพื่อแลกเปลี่ยนข้อมูล และให้กรอบการตั้ง performance objective/requirement ด้าน reliability/availability (cl. 1, p.1)
- กำหนด **ข้อมูลขั้นต่ำ** ที่ต้องเก็บ แบ่ง 3 กลุ่ม: (a) equipment data เช่น taxonomy, attributes (b) failure data เช่น failure cause, consequence (c) maintenance data เช่น action, resource, consequence, down time (cl. 1, p.1; รายละเอียดอยู่ใน Clause 9)
- พื้นที่ใช้งานข้อมูล: reliability, availability/efficiency, maintenance, safety and environment (cl. 1, p.1)
- **ไม่ครอบคลุม**: ข้อมูล cost โดยตรง, ข้อมูลจาก lab test/manufacturing (เช่น accelerated life test), data sheet ฉบับเต็ม, ข้อมูล on-service เพิ่มเติมตามที่ operator อยากได้เอง, และวิธีวิเคราะห์ข้อมูล (แต่ Annex C ให้หลักคำนวณ parameter พื้นฐาน) (cl. 1, p.1-2)
- Normative reference เดียว: ISO 20815:2008 (production assurance) (cl. 2, p.2)

## Clause 3 Terms and definitions: คำที่สำคัญต่อ wiki (p.2-18)

คำนิยามส่วนใหญ่ดัดแปลงจาก IEC 60050-192:2015 และ ISO/TR 12489:2013 รายละเอียดการตีความเวลา/availability อยู่ใน Annex C และ Figure 4 / Table 4

### กลุ่ม failure

| Term (cl.) | สรุปความหมาย (paraphrase) |
|---|---|
| failure (3.23, p.6) | การสูญเสียความสามารถในการทำงานตามที่ต้องการ เป็น **event**; ต่างจาก fault ซึ่งเป็น **state**; ไม่ใช้กับ item ที่เป็น software ล้วน |
| fault (3.33, p.7) | สภาพที่ทำงานตามต้องการไม่ได้เพราะสถานะภายใน อาจเกิดจาก failure หรือจากข้อบกพร่องช่วง spec/design/manufacture/maintenance โดยไม่ต้องมี failure ก็ได้ |
| failure mode (3.30, p.7) | ลักษณะ/อาการที่ความล้มเหลวเกิดขึ้น รายการโหมดต่อ equipment class อยู่ใน B.2.6; การวิเคราะห์อาจต้องเก็บโหมดในหลาย taxonomy level (Table 3) |
| failure mechanism (3.29, p.7) | กระบวนการ (physical, chemical, logical หรือผสม) ที่นำไปสู่ failure; รายการใน B.2.2 / Table B.2 |
| failure cause (3.24, p.6) | ชุดสถานการณ์ที่นำไปสู่ failure; มาตรฐานให้ **"root cause" เป็นชื่อพ้อง**; ต้นกำเนิดได้ทุกช่วง spec ถึง maintenance; รายการใน B.2.3 / Table B.3 |
| failure impact (3.28, p.6) | ผลของ failure ต่อ function ของ equipment หรือต่อ plant; ระดับ equipment แบ่ง 3 ชั้น critical / degraded / incipient (Table 3) |
| critical failure (3.9, p.3) | failure ระดับ equipment unit ที่ทำให้หยุดทำ required function ทันที (รวมกรณีต้องสั่งหยุดทันทีแม้ยังเดินได้ชั่วครู่) และนำไปสู่ unscheduled repair |
| degraded failure (3.11, p.4) | ไม่ทำให้ function หลักหยุด แต่ลดทอน function บางส่วน (output ต่ำ/สูง/ไม่นิ่ง) เลื่อนซ่อมได้ แต่ถ้าปล่อยอาจกลายเป็น critical |
| incipient failure (3.40, p.9) | ความไม่สมบูรณ์ของสภาพที่อาจ (หรือไม่) พัฒนาเป็น degraded/critical ถ้าไม่แก้; ต้องมีเกณฑ์ชัดว่าเมื่อไรต้องบันทึก |
| non-critical failure (3.68, p.13-14) | failure ที่ไม่ทำให้หยุดทันที = degraded + incipient; คำว่า "critical" ในมาตรฐานนี้ **ความหมายไม่เหมือน** ISO/TR 12489 (F.4.1) |
| hidden failure (3.35, p.8) / latent fault (3.44, p.9) | failure ที่ O&M ไม่เห็นทันที มักพบเมื่อ demand/test; latent fault = fault ที่ยังไม่ปรากฏ |
| failure on demand (3.31) / failure due to demand (3.26) (p.6-7) | on demand รวมทั้ง failure ที่เกิดก่อน demand และที่เกิดเพราะ demand |
| common cause (3.5) vs common mode (3.6) (p.3) | common cause = หลาย item เสียจากสาเหตุเดียว; common mode = หลาย item เสียด้วย failure mode เดียวกัน (สาเหตุต่างได้) ทั้งคู่ลดประสิทธิผลของ redundancy |
| random (3.79) / systematic failure (3.90) (p.15, 17) | systematic = เกิดซ้ำภายใต้เงื่อนไขการใช้/จัดเก็บเฉพาะ; reliability data ครอบคลุมทั้งสองแบบ |
| detection method (3.14, p.4) | วิธีที่ค้นพบ failure เช่น periodic test, continuous CM (Table B.4) |
| trip (3.93, p.17) | หยุดเครื่องอัตโนมัติจากสภาวะปกติจนหยุดสนิท แยก real trip (ค่าเกิน set point จริง) กับ spurious trip (เกิดจาก failure ของระบบควบคุม หรือ error จากคน/สภาพแวดล้อม) |

| item (3.43, p.9) | คำรวมสำหรับ level 6-9 ของ taxonomy อาจเป็น hardware, software, คน หรือผสม |

### กลุ่มเวลาและตัวชี้วัด

| Term (cl.) | สรุป |
|---|---|
| down time (3.16, p.5) | ช่วงที่ item อยู่ใน down state รวมทุก delay จาก failure จนกลับมาให้บริการ แยก planned/unplanned (Table 4) |
| down state (3.15, p.4) | ทำงานตามต้องการไม่ได้เพราะ fault ภายใน **หรือ PM** |
| up time / up state (3.96-3.97, p.18) | ช่วง/สถานะที่พร้อมทำงาน |
| operating time (3.70, p.14) | ช่วงที่อยู่ใน operating state รวมทั้งเดินจริงและพร้อมทำ function; ต้องระบุหน่วย (เวลา, cycle ฯลฯ) และจุดเริ่มนับ (ติดตั้ง/commission/เริ่มผลิต) |
| idle time (3.38-3.39, p.8-9) | up state ช่วงที่ไม่ต้องการใช้งาน; non-operating time = idle + standby + externally disabled |
| active maintenance time (3.1, p.2) | ระยะเวลาทำงานบำรุงรักษา **ไม่รวม logistic delay** แต่ **รวม technical delay** |
| active repair time (3.2, p.2) | เวลาที่ใช้ซ่อมจริง (effective) |
| logistic delay (3.46, p.10) | delay จากการจัดหาทรัพยากร (เดินทาง, รออะไหล่/ช่าง/เครื่องมือ, รอสภาพอากาศ) ไม่รวม administrative delay |
| mobilization time (3.66, p.13) | เวลารวบรวมทรัพยากรก่อนเริ่มงาน (อะไหล่ เครื่องมือ คน เรือ) |
| MART (3.59, p.12) | ค่าคาดหมายของ active repair time |
| MRT mean overall repairing time (3.61, p.12) | ค่าคาดหมายของ (เวลาก่อนเริ่มซ่อม + เวลาซ่อมจริง + เวลาก่อนส่งคืน operation) |
| MTTR mean time to repair (3.63, p.12-13) | ค่าคาดหมายเวลาจนซ่อม item เสร็จ; ในทางปฏิบัติเวลา detect เป็น 0 หรือไม่ทราบ จึง **เก็บได้จริงแค่ MRT และ MART** |
| MTTRes mean time to restoration (3.64, p.13) | MRT + **เวลาตรวจพบ failure**; IEC 60050-192 ย่อคำนี้ว่า MTTR ด้วย (ชื่อชน) |
| MTTF (3.62, p.12) | ค่าคาดหมายเวลาก่อนเสีย (IEC: operating time to failure) |
| METBF (3.60, p.12) | ค่าคาดหมาย **elapsed time** ระหว่าง failure ต่อเนื่องของ repairable item; IEC นิยาม MTBF/MOTBF เป็น **operating time** ระหว่าง failure |
| MCTF / mean number of cycles (3.57-3.58, p.11) | ตัวชี้วัดเชิง cycle สำหรับอุปกรณ์ที่นับเป็นรอบ |
| failure rate (3.32, p.7) vs failure frequency (3.27, p.6) | failure rate = ความน่าจะเป็นต่อหน่วยเวลาแบบมีเงื่อนไขว่ายังทำงานตลอด [0,t] (hazard); failure frequency = unconditional intensity (ทำงานที่เวลา 0) หรือ rate of occurrence |
| design life (3.13, p.4) | อายุใช้งานที่วางแผนของทั้งระบบ **อย่าสับสนกับ MTTF** |
| maintenance man-hours (3.53, p.11) | ผลรวมชั่วโมงทุกคน ไม่สัมพันธ์ตรงกับ MTTR/MDT เพราะหลายคนทำพร้อมกัน |
| surveillance period (3.89, p.17) | ช่วงปฏิทินระหว่างวันเริ่มกับวันจบการเก็บข้อมูล |

### กลุ่ม maintenance

- maintenance (3.49), corrective (3.8, หลังตรวจพบ fault เพื่อคืนสภาพ), preventive PM (3.78, เพื่อลด degradation และโอกาสเสีย), CBM (3.7, PM อิงการประเมินสภาพ ทั้งโดยคนหรือ CM), planned/scheduled (3.76), predictive PdM (3.77, ทำนายสภาพในอนาคตจากข้อมูลอดีต), opportunity maintenance (3.71), periodic/proof test (3.74) (p.3, 14-15)
- maintenance impact (3.52, p.11): ระดับ equipment แบ่ง critical/non-critical; ระดับ plant แบ่ง total/partial/zero
- **modification** (3.67, p.13) ไม่ใช่ maintenance แม้ช่างจะเป็นคนทำ ต้องแยกออกจากงานซ่อมเพราะ failure เมื่อวิเคราะห์ข้อมูล
- human error (3.36), human fatigue (3.37), software error (3.87) มีนิยามแยกและโยงกับ failure cause ใน Table B.3 / mechanism ใน Table B.2

## Clause 5 Application (p.20-23)

- **Equipment coverage** (5.1, p.20): process equipment & piping, safety, subsea, pipeline, loading/unloading, downhole well, drilling; ทั้งติดตั้งถาวรและใช้ชั่วคราว ตัวอย่างใน Annex A; ผู้ใช้ควรสร้าง taxonomy ของ class ใหม่เองตามหลักเดียวกัน; ข้อมูลระดับ plant/system ต้องใช้ข้อมูลอื่นเพิ่ม
- **Time periods** (5.2, p.20): ครอบคลุม installation, start-up, operation, maintenance, modification; ไม่ครอบคลุม lab/fabrication แต่หลักการใช้กับ NCR ช่วง acceptance test ได้
- **Users** (5.3, p.21): facility, owner/operator, industry (JIP), manufacturer, regulator, consultant; ผู้ใช้หลักคือ owner/operator
- **Limitations** (5.4, p.21-22): ไม่ใช่คู่มือวิธีวิเคราะห์ ไม่รวม cost data (ให้ไปเอาจาก CMMIS), ไม่ใช่ spec ซอฟต์แวร์ และไม่ใช่มาตรฐานการเขียน maintenance programme
- **Exchange of RM data** (5.5, p.22-23): แลกได้ทั้งระดับ record และระดับสรุป/KPI (Annex E); ข้อมูลอ่อนไหวให้ blank หรือทำ anonymous code; ระวัง **competition law** (ห้ามใช้ benchmarking ไปจัดอันดับ supplier จนเกิด collective boycott); ต้องมี data security; วัด "value of data" ได้จาก cost การเก็บ หรือ population x surveillance time

## Clause 6 Benefits (p.23-25)

- ความชัดเจนเรื่องสาเหตุ failure ช่วยจัดลำดับงานแก้ไข → reliability, กำไร, safety ดีขึ้น; ใช้ optimize ช่วง overhaul/inspection, เนื้อหา procedure, LCC ของ spare/upgrade (p.23)
- การเก็บข้อมูลมีต้นทุน ต้องชั่งกับประโยชน์ และเลือกอุปกรณ์ที่ผลของ failure กระทบ safety, production, environment หรือมีค่าซ่อมสูง (p.23)
- Figure 1: feedback loop ของการใช้ข้อมูลเพื่อ continuous improvement; ประโยชน์จัดกลุ่ม economic, general, safety/environment, analytical (เช่น ขยาย test interval ตาม RM performance, เป็นฐาน RBI/RAM) (p.24-25)

## Clause 7 Quality of data (p.25-28)

### 7.1.1 ลักษณะข้อมูลคุณภาพสูง (p.25)
ครบตาม spec; ตรงกับนิยาม/รูปแบบ; ป้อน-ส่ง-เก็บถูกต้อง; population และ surveillance period พอให้มั่นใจทางสถิติ; ตรงกับความต้องการผู้ใช้

### 7.1.2 Planning measures ก่อนเริ่มเก็บ (p.25-26)
- ตั้งวัตถุประสงค์ (QRA, RAM, RCM, LCC, SIL), ตรวจแหล่งข้อมูล, กำหนด taxonomy และ **boundary ต่อ class** (Clause 8), ระบุวันติดตั้ง/population/ช่วงเวลาใช้งาน
- ใช้ **นิยาม failure และวิธีจัดประเภท failure/maintenance แบบเดียวกันทั้งหมด** (Clause 9)
- รายการตรวจขั้นต่ำ 9 ข้อ (สรุป): origin traceable; อุปกรณ์/เทคโนโลยี/สภาวะคล้ายกัน; อุปกรณ์ยังเกี่ยวข้อง (ไม่ล้าสมัย); ตรงนิยาม; failure อยู่ใน boundary และ surveillance period; **ข้อมูลสอดคล้องกัน เช่น failure mode กับ failure impact**; format ถูก; ข้อมูลพอทางสถิติ ไม่ถูก outlier ลาก (C.3.2); ให้ O&M ช่วย validate
- จัดลำดับความสำคัญความครบของข้อมูล 3 ระดับ: HIGH บังคับ ~100%, MEDIUM >85%, LOW >50% (p.26)
- ความละเอียดข้อมูลผูกกับความสำคัญด้าน safety/production; ทำแผน (schedule, ลำดับ, วิธีโอนข้อมูล); อบรมผู้เก็บ; แผน QA; แนะนำทำ **pilot** เพื่อดู cost-benefit; ทบทวนแผนหลังใช้งานระยะหนึ่ง

### 7.1.3 Verification (p.26-27)
ตรวจระหว่างและหลังเก็บ (consistency, การกระจายสมเหตุผล, code ถูก) และต้องบันทึกเป็นเอกสาร; รวมหลาย database ต้องมี unique ID ต่อ record; ประเมินเร็วที่สุดเพื่อแก้แผนทัน; **ผู้ตรวจต้องไม่ใช่คนเดียวกับผู้เก็บ**

### 7.1.4 Table 1 ปัญหา (p.27)
Source กระจัดกระจาย; การตีความต่างกันระหว่างคน; **ใช้ coded field เป็นหลักและมี free text เสริม**; การโอนข้อมูลกึ่งอัตโนมัติจาก CMMIS; ความสามารถและแรงจูงใจของผู้เก็บ

### 7.2 Data collection process (p.27-28)
- 7.2.1 แหล่งหลักคือ **facility CMMIS** ซึ่งต้องรองรับการรายงานตามมาตรฐานนี้; ประเภทแหล่งตาม Table D.5: generic, operator-specific, manufacturer, expert judgement, human error data
- 7.2.2 วิธีเก็บทั่วไป: ดึง raw data ลง intermediate storage → ตีความ/แปลงเข้ารูปแบบเป้าหมาย (ส่วนใหญ่ทำมือ) → โอนเข้า reliability data bank (อัตโนมัติคุ้มเฉพาะข้อมูลปริมาณมาก/ซ้ำ) → วางแผนและทดสอบวิธีก่อนเริ่มจริง
- 7.2.3 ต้องมีทักษะ IT, สถิติ, maintenance, operation; มีระบบจัดการ deviation (นิยามกำกวม, code ไม่พอ) ตั้งแต่ต้น; สรุป lessons learned ป้อนกลับไปปรับนิยาม, CMMIS และกระบวนการ
