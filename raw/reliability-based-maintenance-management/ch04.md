# บทที่ 4 ระบบบริหารงานบำรุงรักษาโดยโปรแกรมคอมพิวเตอร์ (CMMS)

Source: วัฒนา เชียงกูล et al., "การจัดการงานบำรุงรักษาด้วย Reliability" (SE-ED 2553), PDF p091-p114 = book p.89-112. (p091 = หน้าชื่อบท)

## บทนำบท (book p.90)
- MMS เป็นส่วนสนับสนุนกิจกรรมบำรุงรักษา 16 กิจกรรม (บทที่ 1); เมื่อใช้คอมพิวเตอร์เรียก CMMS ซึ่งเป็น software สำเร็จรูปคล้ายระบบบัญชี
- CMMS ส่วนใหญ่ใช้ไม่คุ้มค่า (ประมาณไม่ถึงครึ่ง) เพราะไม่ครบวงจร: เก็บข้อมูลโดยขาดการวิเคราะห์งานบำรุงรักษา -> ไม่เห็นคุณค่าข้อมูล เก็บผิดตัว (ที่ต้องใช้ไม่เก็บ ที่เก็บไม่ใช้) ข้อมูลไม่ทันสมัย
- บทนี้เน้นบทบาท CMMS ทั้งการควบคุม Process และเนื้อหาข้อมูล (Content)
- หัวข้อ: ความคาดหวัง, สิ่งที่ทำไม่ได้/ได้, CMMS Modules, ทำให้คุ้มค่า, คุณภาพข้อมูล, CMMS ใน RAM, ข้อมูลสำคัญ, ผลลัพธ์การวิเคราะห์

## ความคาดหวังจาก CMMS (book p.90)
- เหตุผลที่โรงงานนำ CMMS มาใช้: ลด Down Time, ต้องการรู้ค่าใช้จ่ายบำรุงรักษา, ลดงานล่วงเวลา, ให้สอดคล้อง ISO 9000, TPM Autonomous ระดับ 4 ต้องมี software, ลดผลกระทบจากช่างลาออกบ่อย (เก็บความรู้ในระบบ)

## สิ่งที่ CMMS ทำไม่ได้ / ทำได้ (book p.91-92)
- ความเข้าใจผิด: คิดว่า CMMS เป็นยาวิเศษ; จริงๆ เป็นเพียง Housekeeping software เหมือนระบบบัญชี
- ประเด็นหลักคือความเข้าใจงานบำรุงรักษาทั้ง process และ content; ไม่รู้งานจริงๆ ซื้อ software แพงก็ไม่ดีขึ้น (เช่น มีระบบบัญชีแต่ยังขาดทุน, มี CMMS แต่ Breakdown ยังสูง)
- ทำไม่ได้:
  - ไม่บอกว่าควรเลือกงานแบบไหน เมื่อไหร่ กับเครื่องไหน
  - ไม่แยกแยะความถูกต้องของข้อมูล (เก็บทุกอย่างรวมทั้งขยะ)
  - ไม่รับประกันว่าบำรุงรักษาได้ดี (เหมือนบัญชีที่ถูกต้องไม่ได้แปลว่าธุรกิจรอด)
  - ไม่ติดตามความก้าวหน้างานเอง ต้องมีคนป้อนข้อมูลให้ทันความจริง
  - ออกรายงานได้เท่าที่ข้อมูลป้อนเข้าไป
- ทำได้:
  - เก็บข้อมูลมากใน Register รวมประวัติซ่อมทั้งหมด ขยายได้ตามต้องการ
  - ค้นหา/ดูข้อมูลหลายรูปแบบเร็วขึ้น
  - ควบคุมกระบวนการบำรุงรักษาง่ายขึ้น (ระวังว่าจัดงานง่ายเกินไปอาจ over-maintain ส่งผลลบต่อเครื่องจักร)
  - ออกรายงาน/ทำซ้ำเร็ว; สั่งงานง่าย เก็บข้อมูลป้อนกลับเมื่องานเสร็จเป็นประวัติซ่อม (ตามที่สั่งให้เก็บ)

## CMMS Modules (book p.92-94)
10 โมดูลทั่วไป:
| # | Module | สาระ |
|---|---|---|
| 1 | Master Data | ข้อมูลเริ่มต้นระบบ เช่น Cost Center |
| 2 | Access Control | กำหนดผู้ใช้/สิทธิ์ฟังก์ชัน ลดสับสน ป้องกันข้อมูลสำคัญ; ERP ซับซ้อนกว่า software เน้น content |
| 3 | Asset Registration | ข้อมูลหลักที่ต้องทำก่อน; ต้องลงทะเบียน แยกความสำคัญ จัดหมวดหมู่; ถ้าเริ่มไม่ดี รายงานไม่เหมาะสม; ละเอียดเกินไป -> งานมาก; มักใช้เวลานานที่สุดใน implement |
| 4 | Work Control System | สำคัญมาก ถ้าใช้ไม่ได้ถือว่า implement ล้มเหลว; เก็บข้อมูลงานประจำวัน ข้อมูลวิเคราะห์ส่วนใหญ่มาจากที่นี่; แบ่งเป็น Work Request/Maintenance Notification (จุดกำเนิด Unplanned Work) และ Work Order |
| 5 | Planned Maintenance | เตรียมข้อมูลงานตามแผน (Planned Work) + เงื่อนไขออกงาน เพื่อส่งเข้า Work Control ตามกำหนด; ผู้ใช้มักคิดว่าสำคัญที่สุด แต่ Work Control สำคัญกว่า เพราะเป็นโครงสร้างพื้นฐานการวิเคราะห์ปรับปรุง (รวม PM) |
| 6 | Spare Part Management | ซ่อมต้องมีอะไหล่เสมอ; แผนงานชัด งานนอกแผนน้อย -> ไม่ต้องสต๊อกเกิน ลดค่าถือครอง |
| 7 | Purchasing System | จริงๆ เป็นส่วนของบัญชี แต่โรงงาน Continuous Process ซื้ออะไหล่มาก บางซอฟต์แวร์รวมมาด้วย (ซับซ้อน ต้อง verify ข้อมูลส่งบัญชี); สิ่งที่บำรุงรักษาต้องการคือ Purchase Requisition มากกว่า Purchasing |
| 8 | Report and KPI Analysis | สำคัญสุด ผลลัพธ์ที่จับต้องได้คือรายงานและวิเคราะห์ ใช้ปรับปรุงการบริหาร ชี้วัดขนาดองค์กร ปรับปรุงทรัพย์สิน |
| 9 | Maintenance Performance Budgeting | ทำ/ควบคุมงบ มักอยู่ใน ERP; ควรใช้ Activity Based Budgeting (งานบริการผ่าน Man-Hrs); ต้องได้ทั้ง efficiency ของกิจกรรมและ effectiveness ต่อทรัพย์สิน |
| 10 | Turnaround Management | บริหารงานหยุดเครื่องซ่อมใหญ่ (เฉพาะซอฟต์แวร์โรงงานใหญ่) |
- จำนวนโมดูลต่างกันตามผลิตภัณฑ์; หนังสือเน้นโมดูลจำเป็น
- รูปที่ 4.1 (p.94): Core modules = Asset Register (Asset Database), Work Order Backlog, Work Order History, Planned Maintenance, Spare Part Management, Report & Analysis. สำคัญสุดคือ Work Order Backlog + History (ข้อมูลระดับ Shop Floor สำหรับวิเคราะห์ระยะยาว). แผนภาพ: Work Request -> Work Order Backlog (สถานะ Initiated, Planned, Scheduled, Executed, Finished, Completed) <-> กล่อง Wait (Wait for Material/Shutdown/Others); Asset Database ป้อนเข้า Backlog; Planned Maintenance (PM Task, PM Resource, Scheduling Criteria) ส่ง Schedule of PM Work Order เข้า Backlog; Turn Around Management ป้อน Backlog; Spare Parts Management (Spare Part Master, Inventory Transaction, Purchase Requisition) <-> Purchasing System; Backlog <-> Work Order History -> Report & Analysis

## การทำให้ CMMS ทำงานคุ้มค่า (book p.94-95)
- องค์ประกอบ: (1) ฐานข้อมูล+กระบวนการบำรุงรักษาที่ชัดเจน (Maintenance Process) (2) ควบคุมคุณภาพข้อมูล (Data Content)
- ระบบประกอบ 3 ส่วน (รูปที่ 4.2 พีระมิด p.95): 
  1. ฐานข้อมูล (ล่าง): ข้อมูลเครื่องจักรอุปกรณ์ -> ข้อมูลงาน Planned Maintenance -> ข้อมูลพัสดุอะไหล่
  2. ระบบงานและข้อมูลประจำวัน: ระบบควบคุมงานบำรุงรักษา -> ระบบบริหารพัสดุอะไหล่
  3. ผลลัพธ์และการวิเคราะห์ (บน): รายงานและการวิเคราะห์ -> งบประมาณและการ Optimize
- ผลจากส่วน 3 ย้อนกลับปรับปรุงคุณภาพข้อมูลและระบบงานส่วน 1-2
- ฐานข้อมูลหลัก: Asset Database, Planned Maintenance Database, Spare Part Database

## Asset Register (book p.96-99)
- แบ่ง 2 ส่วน: (1) ข้อมูลเครื่องจักร (2) โครงสร้างเครื่องจักร
- ข้อ 1: เริ่มระบบได้ถ้ามีรายการเครื่องจักรและรหัสครบ ข้อมูลอื่นเป็น Static เพิ่มทีหลังได้ -> เป็นกลยุทธ์ให้ขึ้นระบบเร็ว
- รูปที่ 4.3 (p.96) ข้อมูลสำคัญของเครื่องจักร: 
  - Equipment Database (ข้อมูลที่สร้างครั้งแรก): Criticality -> Maintenance Strategy; Structure & Coding -> Report & Analysis; Accounting Info -> Accounting & Report; BOM -> Spare Part Analysis; Technical Data -> Technical Information
  - Equipment Maintenance History (ข้อมูลที่ได้จากการทำงาน/Transaction): Work Type -> Report & Analysis; Failure Data (Failure Mode, Object Part, Cause, Effect, Consequence, Effect Cost) -> Failure Analysis, Maintenance Optimization, Spare Optimization; Resources Cost (Stock, Non-Stock, Outsource, Man Hours) -> Maintenance Cost Analysis; Time (Down Time, Work Time, Wait Time) -> Problem & Work Analysis; Work Description -> Technical Information
- 2.1 โครงสร้างความสัมพันธ์ (p.96-98): ระบบเอกสารแบบ manual ใช้รายชื่อพอ; ใน CMMS จัดเป็น Hierarchy: Area -> Process -> Equipment -> Component -> Part (รูปที่ 4.4)
  - 2 ระดับใหญ่: Productive Unit/Location (Logical Asset; ไม่มีตัวตนจริง ใช้จัดกลุ่มเพื่อค้นหา/รายงาน) และ Equipment/Maintainable Item (Physical Asset; จับต้องและซ่อมแซมได้)
  - ยิ่งละเอียด ภาระข้อมูลยิ่งมาก -> รูปที่ 4.5: Hierarchy หยุดที่ระดับ Equipment; ระดับต่ำกว่า (Component/Part) ใช้เป็น "Object Part" / "ตำแหน่งปัญหา" ระบุในประวัติซ่อมแทนการกำหนดในโครงสร้าง
  - อะไหล่ไม่ควรอยู่ใน Hierarchy ให้ไปอยู่ใน Bill of Material (อะไหล่เดียวใช้หลายอุปกรณ์)
- 2.2 Coding Structure (p.98-99) แนวทาง:
  - รหัส Productive Unit/Location เป็น Smart Number (แต่ละ digit มีความหมาย ใช้วิเคราะห์เชิงจัดการ)
  - รหัส Maintainable/Serial Level เป็นอิสระ (Running Number) ไม่อิง Location เพราะย้ายตำแหน่งบ่อย
  - ไม่ฝังรหัสบัญชี/ทรัพย์สิน, รหัสแผนก, รหัสอะไหล่ ลงในรหัสอุปกรณ์ (เปลี่ยนองค์กร/ผู้ผลิตแล้วเสียโครงสร้าง; มุมมองบัญชีกับซ่อมบำรุงต่างกัน)
  - รูปที่ 4.6: ตัวอย่าง Smart Number รูปแบบ XX-999-AA ที่ระดับ Area/Process; Running Number เช่น MOT2499 ที่ระดับ Equipment

## Planned Maintenance Database (book p.99-100)
- หลักสำคัญ: "งานอะไรที่ทำแล้วบอกไม่ได้ว่าสู้กับ Failure Mode ไหน ก็ไม่จำเป็นต้องทำ"
- ข้อมูล PM 3 กลุ่ม: (1) PM Activity - ทำอะไรกับ Equipment/Object Part ไหน เพื่อยับยั้ง Failure Mode อะไร (2) ระยะเวลา PM - เริ่มจากคำแนะนำผู้ผลิต ปรับตาม Operating Context โดยวิเคราะห์ประวัติเสียที่ Object Part + Failure Mode เดียวกัน (3) ข้อมูลทรัพยากร (อะไหล่ กำลังคน) - มักถูกมองข้าม แต่มีประโยชน์วางแผนทรัพยากรระยะยาวและงบ
- รูปที่ 4.7: PM Task + ประเภทปัญหา (Problem) ชี้ลงที่ Object Part ใน Hierarchy
- PM จ่ายผ่าน Work Control; หน้าที่ PM = เลือก task ให้ตรง Failure Mode + กำหนดคาบ และจัดกลุ่มงาน (Task ย่อยจำนวนมากต้องรวมเป็น package) ให้ใช้ทรัพยากรคุ้มค่า

## Spare Part Database (book p.100-102)
- ปัญหาทั่วไป: อะไหล่ที่ต้องการไม่มีให้เบิก, ที่มีไม่เคยเบิก, ของไม่ตรง Stock Card, อะไหล่ล้นแต่ยังรออะไหล่
- เป้าหมายขัดกัน: Stock Level ต่ำสุด vs Stock Availability/Service Level สูงสุด vs Stock Turnover สูงสุด vs Plant Availability สูงสุด -> ใช้ Optimization หาจุดสมดุล
- ข้อมูลพัสดุ = Spare Part Database + Inventory Transaction. ฐานข้อมูลอะไหล่ 3 ส่วน:
  1. ข้อมูลเฉพาะรายการ (รหัส ชื่อ รายละเอียด คุณสมบัติ วิธีเก็บ ประเภท สถานที่เก็บ) - ไม่แก้บ่อย
  2. ข้อมูลที่เปลี่ยนจาก Transaction (จำนวนคงเหลือ ต้นทุนต่อหน่วย มูลค่า วันที่เบิกล่าสุด Lead Time อายุอะไหล่) - แก้โดยตรงไม่ได้ ต้องผ่าน transaction เพื่อตรวจสอบย้อนกลับ
  3. ข้อมูลกำหนดระดับจัดเก็บ: Max, Min, ROP (จุดสั่งซื้อ), EOQ - ประเมินช่วงแรกโดยผู้มีประสบการณ์ แล้วคำนวณจากสถิติเมื่อมีข้อมูลเบิก (วิธีคำนวณในบทถัดไป)
- ข้อมูลเสริม: Where Used/BOM, ผู้ขายและประวัติซื้อ, อะไหล่ทดแทน (ทางเดียว/สองทาง)
- รูปที่ 4.8 (p.102) ฐานข้อมูลอะไหล่: กลุ่ม 1 (สร้างครั้งแรก) Part Number, Part Name, Spec/วิธีเก็บ, ประเภท/กลุ่ม, Bin Location; กลุ่ม 2 (จากซื้อ รับ จ่าย ปรับปรุง) On hand Qty, Unit Cost, Amount, วันที่เบิกล่าสุด, Lead Time, อายุอะไหล่; กลุ่ม 3 (จากการคำนวณ - Spare Optimization Recommendation) Min Qty, Max Qty, Re-Order Point, EOQ
- Inventory Transaction (รูปที่ 4.9 p.103): แบ่ง 2 ประเภท: (ก) กระทบจำนวนคงเหลือ: รับ จ่าย ปรับปรุง; (ข) ไม่กระทบคงเหลือโดยตรงแต่กระทบ Available: ยืม (Borrow), จอง (Reserve), ขอซื้อ (PR), ตรวจรับเบื้องต้น (Dock Receive)
  - ฟิลด์: ประเภทรายการ (เบิก/รับ/ปรับปรุง), Part Number, Part Name, วันที่, จำนวน, Unit Cost, มูลค่า, Work Order Number, เครื่องจักร/อุปกรณ์, Cost Center, รหัสบัญชี, หน่วยงาน

## Maintenance Process (book p.103-105)
- Process คือแนวปฏิบัติที่ชัดเจน ทำซ้ำได้ ใช้สอนคนใหม่; ถ้าซับซ้อนก็ล้มเหลว
- แนวทาง: อย่าให้ซับซ้อนจนปฏิบัติยาก (การเปลี่ยนมักถูกต่อต้าน); ลดจุด Approve ให้น้อยที่สุด (ช่างอยู่หน้าเครื่องไม่ใช่หน้าคอมฯ); จุดอนุมัติมักอยู่ที่การส่งผ่านหน่วยงาน (อนุมัติแจ้งซ่อม, ค่าใช้จ่าย, ปิดงาน, แก้ข้อมูลสำคัญ)
- รูปที่ 4.10 Maintenance Work Flow 1 (p.104): Production ออก Work Request -> ถ้า Breakdown (Yes) ออก WO โดย Production (BM) ตรงไป Print WO; ถ้าไม่ใช่ -> Maintenance Approve? (No -> Work Request History) -> Initiate WO -> Plan Resource (รับ PM Task/Schedule of PM WO) -> Assign & Schedule (Stock Reserve from WO) -> Print WO -> Safety work? (Yes -> WO with Permit to Work: Hot Work Permit, LOTO/Guarding, Confined Space Permit, Work at Height Permit) -> Execute Work (Issue Stock จาก Spare Parts Control System; PR -> PO System -> Receive Stock) -> Finish Work -> Failure Information -> Approve -> Close to History. มีจุดอนุมัติ 2 จุดเท่านั้น: อนุมัติแจ้งซ่อม และอนุมัติปิดงาน (จุดตรวจความครบถ้วนข้อมูลสำหรับวิเคราะห์)
- รูปที่ 4.11 Workflow 2 (swimlane Production/Maintenance/Store): ผู้แจ้ง -> Engineer/Supervisor ประเมินและออก WO -> Are part required? -> Are part available? (ไม่มี: สั่งอะไหล่/Store initiate PO -> approve PO -> Procurement) -> Issue part -> Mechanic ทำเสร็จ -> Engineer Close WO to History; แสดงวงจรคลังอะไหล่ด้วย

## Work Planning and Control System (book p.105-106)
- รับงานตามแผน (PM ถึงกำหนด) และงานนอกแผน (ผ่าน Work Request) -> จัดลำดับตามความเร่งด่วนและทรัพยากร (Estimate & Schedule) -> ออก WO
- งานทั้งหมดเป็น Backlog จนเสร็จ; ข้อมูล Man-Hrs อะไหล่ Outsource Failure Mode ฯลฯ ต้องบันทึกครบแล้วจึงปิดเข้าประวัติ
- Planned Maintenance = กระบวนการสร้างงานตามแผน (ขั้นตอน ทรัพยากร เงื่อนไข Due, Master Plan); วิธีออกงาน: เตือนเมื่อถึงกำหนด (เตือนตลอดจะน่ารำคาญ) หรือใช้ระบบตะกร้างาน
- ตะกร้างาน (รูปที่ 4.12 Work Backlog Basket): งานค้าง = New Work In System -> Work In Planning -> Work In Scheduling -> Work In Progress -> Work In Approval (รอตรวจสอบปิดงาน) -> Maintenance History; งานรอ (Wait) = Wait for Material / Wait for Shutdown / Wait for Others — แยกสถานะรอภายใน Backlog เพื่อให้ผู้รับผิดชอบติดตาม
- Work Planning and Control เป็นโมดูลสำคัญที่สุด; ถ้าใช้ไม่ได้ = implement ล้มเหลว

## CMMS และบทบาทของ CMMS ใน RAM (book p.106-108)
- รูปที่ 4.13 Reliability Based Asset Management Model (RAM): กรอบเส้นประ = ส่วนที่ CMMS ครอบคลุม (Registration of Assets/Asset register; Maintenance Requests -> Work Packaging, Executing & Control -> Scheduled PMs, CM-Unplanned, Maintenance History, Costs)
- 7 กระบวนการใน RAM:
  1. ลงทะเบียนทรัพย์สิน (Register)
  2-4. Criticality Assessment/เลือก Asset ตาม Criticality -> Functional Performance + Operating Context -> Evaluation of Failure Consequences (Safety, Hidden, Operational, Non-Operational) -> Task Selection (Scheduled Condition Monitoring, Scheduled Part Replacement, Scheduled Overhaul, Scheduled Failure Finding; ไม่ผ่านเลือก Run To Fail หรือ Redesign) — 3 กระบวนการนี้มักไม่อยู่ใน CMMS เพราะต้องใช้ความรู้เรื่องอุปกรณ์/กระบวนการผลิต แต่ขาดไม่ได้; ถ้าขาด PM จะมาจาก "น่าจะทำ"/คำแนะนำผู้ผลิต ทำให้ PM มากโดยไม่รู้จุดประสงค์
  5. Work Packaging, Executing & Control (ควบคุมงานตามแผน+นอกแผน จัดงาน วางแผนทรัพยากร เก็บประวัติ)
  6. Maintenance/Asset Performance Analysis (Age exploitation, Failure Consequences, Inspection Finding reports, Actuarial analysis, Asset Performance Reports, Strategic Reports, Indices)
  7. Application of Engineering Standards (Standardization, Operating Performance requirement, FMECA, Update equipment register) + Redesign/New Technology
- ข้อมูลหลักของ process 6 มาจาก CMMS (ส่วนวิเคราะห์เชิงลึกเช่น Reliability Analysis ทำภายนอก) ปัญหา: วิเคราะห์ไม่ได้เพราะข้อมูลไม่มีคุณภาพ (ไม่รู้ว่าต้องเก็บอะไร)
- ถ้า process 6 / feedback loop ไม่สมบูรณ์ -> CMMS "left open ended" (รูปที่ 4.14) ถูกตัดขาดจาก control process คุณภาพหาย
- p.108: Process 5 = การได้มาของข้อมูล (Process); Process 6 = สร้าง/ปรับเนื้อหาให้มีคุณภาพ (Content) สำคัญเท่ากัน. สร้าง Process ง่าย/เร็ว/ลงทุนไม่มาก; สร้าง Content ที่มีคุณภาพยาก ต้องสร้างคน (อบรม ที่ปรึกษา นำไปใช้จริง ใช้เวลาเป็นปี) — "เรียนเพื่อรู้ ไม่ได้เรียนเพื่อใช้" ไม่ได้ผล
- ปัจจัยตั้งต้นให้ CMMS มีคุณค่า: เป้าหมายบำรุงรักษาที่ถูกต้องตีความได้; วิเคราะห์ผลงานเชิงวิทยาศาสตร์ลงถึงเหตุปัจจัย; ใช้ตัวชี้วัดควบคุมหลายระดับอย่างเหมาะสม

## คุณภาพของข้อมูลบำรุงรักษา (Data Content) เพื่องานวิเคราะห์ (book p.108-110)
- ยากที่สุดคือทำให้ข้อมูลมีคุณภาพ เพราะมาจากผู้ปฏิบัติหลายคน
- ข้อมูลดูแลคุณภาพตัวเองไม่ได้; "ข้อมูลขยะ" = ไม่มีเจ้าของ ไม่มีใครใช้ เก็บโดยไม่รู้จะนำไปทำอะไร; ต้องกลับไปที่การวิเคราะห์งานบำรุงรักษา: ต้องรู้ว่าจะวิเคราะห์ค่าอะไร -> ค่ามาจากไหน -> ทำให้ Reliable Data -> วิเคราะห์ -> แก้ที่เหตุปัจจัย
- ข้อมูลสำคัญใน CMMS 5 กลุ่ม: Work Request, Work Order, เวลา (Down Time, Work Time, Wait Time), ข้อมูลความเสียหาย (Failure Mode, Cause, Effect, Effect Cost), ทรัพยากร (Man-Hrs, Stock, Non-stock, Outsource, Resources Cost)
- รูปที่ 4.15 ข้อมูลจากใบสั่งงาน (p.109):
| กลุ่ม | ฟิลด์ |
|---|---|
| แจ้งซ่อม | Work Request Number, วันที่/เวลาออกใบแจ้งซ่อม, หน่วยงานแจ้ง (Requester Dept), ผู้แจ้ง, Cost Center, อาการ/ปัญหา (Problem Description) |
| สั่งงานซ่อม | Work Order Number, วันที่/เวลาออกใบสั่ง, Work Priority, เครื่องจักร (Productive Unit/Machine), อุปกรณ์ (Equipment), ประเภทงาน, รายละเอียดงานที่ทำ (Work Action), ผู้รับผิดชอบ |
| เวลาหยุดเครื่อง (Down Time) | PU Down Date/Time, PU Start Date/Time, รวม Down Time |
| เวลาปฏิบัติงาน (Work Time) | วันที่/เวลาเริ่ม, เสร็จงาน, รวมเวลาปฏิบัติงาน |
| เวลารอ (Wait Time) | ประเภทการรอ, วันที่/เวลาเริ่มรอ, สิ้นสุดการรอ, รวมเวลารอ |
| ความเสียหายและสาเหตุ | Failure Mode, Cause/Root Cause, Effect, Effect Cost |
| ทรัพยากรที่ใช้ | Maintenance Man Hours แยกตามผู้ปฏิบัติ, Man Hours Cost, อะไหล่เบิกจากคลัง (Stock), อะไหล่ซื้อตรง (Non Stock), Outsource Services |
- ข้อมูลอื่นที่ต้องใช้วิเคราะห์ — จากบำรุงรักษา: Man-Hrs/งาน, อะไหล่/งาน, การวิเคราะห์ Failure Mode/Cause, ประเภทงาน (ตามแผน/นอกแผน), ข้อมูลการเงิน (ค่าเสียหายต่อครั้ง), ประวัติเสียย้อนหลังเพื่อวิเคราะห์ตัวแปรทางสถิติของการเสีย, ประเภท/ความถี่ Scheduled PM. จากหน่วยงานอื่น (p.110): กำหนดการใช้งานเครื่องจักร, อัตราค่าแรงมาตรฐาน (จากบัญชี), อัตราค่าใช้จ่ายบริหารคลังอะไหล่ (% ของมูลค่า), ค่าใช้จ่ายต่อการจัดซื้อแต่ละครั้ง

## การจัดการเรื่อง Failure Mode ใน CMMS (book p.110-111)
- กระบวนการบำรุงรักษาทั้งหมดเกี่ยวกับ Failure Mode จึงต้องวิเคราะห์และเก็บใน CMMS อย่างเป็นระบบเพื่อ update/แก้ไขเสมอ
- รูปที่ 4.16 ความสัมพันธ์ CMMS-RCM: ฝั่ง Foreground (CMMS Housekeeping): Work Initiation -> Work Planning & Scheduling -> Work Execution -> Work Completion/Reporting -> ตัดสิน "Failure Mode of CM-Unplanned Defined?" (Y -> History; N -> Backlog-Failure Mode Undefined วนกลับ). ฝั่ง Background (Maintenance Analysis โดย RCM): RCM-FMECA, Optimization ได้รับ Notification of Important Incident แล้วป้อน Planned work กลับเข้า Work Initiation
- กฎ: ทุก CM-Unplanned ต้องตรวจสอบสรุป Failure Mode; ถ้ายังสรุปไม่ได้ ห้ามปิดงานเป็นอันขาด (ปิดแล้วเป็นประวัติแก้ไม่ได้ และการแก้กระทบยอดระบบอื่น โดยเฉพาะบัญชี); ให้ค้างเป็น Work Order Backlog อีกประเภทจนระบุได้จึงเข้า History
- สาเหตุที่ข้อมูลใน CMMS ไม่ครบ: หน่วยงานไม่ทำวิเคราะห์/ทำน้อยเกินไป -> ไม่รู้ว่าข้อมูลใดสำคัญ

## ความสำคัญของการวิเคราะห์งานบำรุงรักษา (book p.111-112)
- การวิเคราะห์ = กลไกควบคุมคุณภาพ/สมรรถนะหน่วยงานบำรุงรักษา; ปัจจุบันคอมพิวเตอร์ถูกและเชื่อมต่อง่าย ทำสถิติได้ไม่ยาก
- ตัวอย่างการวิเคราะห์: หาตัวแปรสถิติอธิบายการเสียแต่ละ Failure Mode จากข้อมูลอดีต; หา Reliability / Probability of Failure ที่อายุต่างๆ; คำนวณจำนวนครั้งที่คาดว่าเกิดเหตุการณ์ในเวลากำหนด; คำนวณคาบ PM ที่ให้ประโยชน์สูงสุด; คำนวณค่าใช้จ่ายที่คาดในแต่ละกรณี
- ปัญหา: ขาดข้อมูลที่น่าเชื่อถือ

## ผลลัพธ์ที่ต้องการจากการวิเคราะห์ (Maintenance Analysis Results) (book p.112)
- (อย่างน้อย) จำนวนครั้งที่คาดจะทำ Scheduled PM ตามคาบ + ค่าใช้จ่าย; จำนวนครั้งที่คาดว่าจะเสีย (CM-Unplanned) ในช่วงเวลา + ค่าใช้จ่าย; ค่าใช้จ่ายรวม Scheduled PM + CM-Unplanned; Average Availability (%); ค่าใช้จ่ายบำรุงรักษาครบถ้วนต่อชั่วโมงใช้งานได้ของเครื่องจักร

## สรุปท้ายบท (book p.112)
- CMMS = ระบบสนับสนุนด้านเทคนิค ให้คนทำงานกับระบบ ใช้ข้อมูลนำ วิเคราะห์เชิงประสบการณ์ ลดการใช้ความเห็น เพื่อ availability, reliability, safety ที่ต้นทุนเหมาะสม; ต้องมีทั้ง Process และ Content
- ระบบดีแต่ไม่สนใจเนื้อหา = เพิ่มภาระกรอกข้อมูลโดยไม่ได้ประโยชน์; ระบบล้มเหลวมักเกิดจากไม่เข้าใจเนื้อหาที่ถูกต้อง -> เริ่มระบบผิด เกิดระบบย่อยและข้อมูลไร้สาระ
- ต้องสร้างความรู้ Maintenance Engineering ก่อน (ใช้เวลา/ค่าใช้จ่ายมากกว่าสร้างระบบ); เริ่ม CMMS ด้วยความเข้าใจเนื้อหาก่อน

## Key terms
- CMMS (Computerized Maintenance Management System) — ระบบบริหารงานบำรุงรักษาด้วยคอมพิวเตอร์ — software housekeeping สนับสนุนกิจกรรมบำรุงรักษา — p.90
- Process vs Content — กระบวนการ vs เนื้อหาข้อมูล — Process = ขั้นตอนเก็บข้อมูล, Content = คุณภาพ/ความหมายข้อมูล — p.90, 108
- Master Data — ข้อมูลเริ่มต้นระบบ — เช่น Cost Center — p.92
- Access Control — ความปลอดภัยข้อมูล/สิทธิ์ — กำหนดผู้ใช้และฟังก์ชัน — p.92
- Asset Registration / Asset Register — ทะเบียนเครื่องจักรอุปกรณ์ — ข้อมูลหลักที่ต้องทำก่อน — p.92, 96
- Work Request / Maintenance Notification — ใบแจ้งซ่อม — จุดกำเนิด Unplanned Work — p.92
- Work Order — ใบสั่งงานซ่อม — ใบกำกับงานและเก็บประวัติ — p.92
- Work Order Backlog / History — งานค้าง / ประวัติงาน — สถานะงานก่อนปิด / หลังปิด — p.94, 106
- Planned Maintenance — งานบำรุงรักษาตามแผน — PM Task + resource + scheduling criteria — p.92, 94
- Spare Part Management — ระบบบริหารพัสดุอะไหล่ — Master + Inventory Transaction + PR — p.93
- Activity Based Budgeting — งบประมาณตามกิจกรรม — เหมาะกับงานบริการที่ผ่าน Man-Hrs — p.93
- Turnaround Management — งานหยุดซ่อมใหญ่ — p.93
- Productive Unit / Location (Logical Asset) — หน่วยผลิต/ตำแหน่ง — ระดับจัดกลุ่มไม่มีตัวตนจริง — p.97
- Equipment / Maintainable Item (Physical Asset) — อุปกรณ์ที่ซ่อมได้ — ระดับล่างสุดของ Hierarchy — p.97
- Object Part — ตำแหน่งปัญหา — Component/Part ระบุในประวัติซ่อมแทนโครงสร้าง — p.98
- Smart Number / Running Number — รหัสมีความหมาย / รหัสเรียงลำดับ — ใช้กับ Location / Equipment ตามลำดับ — p.98-99
- BOM (Bill of Material) / Where Used — รายการอะไหล่ของอุปกรณ์ / ใช้กับที่ไหน — p.98, 101
- Stock Level / Service Level / Stock Turnover — ระดับคงคลัง / ความพร้อมอะไหล่ / การหมุนเวียน — เป้าหมายขัดกัน ต้อง optimize — p.101
- Min, Max, ROP, EOQ — จำนวนต่ำสุด/สูงสุด จุดสั่งซื้อ ปริมาณสั่งซื้อประหยัด — ค่ากำหนดระดับสต๊อก — p.101-102
- Inventory Transaction — รายการพัสดุประจำวัน — รับ จ่าย ปรับปรุง ยืม จอง PR Dock Receive — p.102-103
- Work Backlog Basket — ตะกร้างาน — Backlog แยกสถานะ + Wait — p.106
- Wait for Material / Shutdown / Others — รออะไหล่ / รอเครื่องหยุด / รออื่นๆ — สถานะงานรอ — p.106
- RAM (Reliability Based Asset Management Model) — แบบจำลองบริหารทรัพย์สินบนพื้นฐาน Reliability — 7 กระบวนการ ที่ CMMS ครอบคลุมเพียงบางส่วน — p.106-107
- Data Content / Reliable Data — คุณภาพข้อมูล / ข้อมูลน่าเชื่อถือ — p.108
- Failure Mode / Cause / Effect / Effect Cost — รูปแบบความเสียหาย / สาเหตุ / ผลกระทบ / ค่าใช้จ่ายจากความเสียหาย — ข้อมูลที่ต้องเก็บใน WO — p.109
- CM-Unplanned — งานซ่อมแก้ไขนอกแผน — ห้ามปิดงานถ้ายังไม่ระบุ Failure Mode — p.111
- Average Availability — ความพร้อมเฉลี่ย (%) — ผลลัพธ์วิเคราะห์ — p.112

## Links to compressor failure hierarchy / OREDA / ISO 14224
- Asset hierarchy (p.96-98, รูปที่ 4.4-4.6): Area/Process (Productive Unit, Logical Asset) -> Equipment (Maintainable Item) -> Component -> Part; Hierarchy หยุดที่ Equipment แล้วใช้ "Object Part" (ตำแหน่งปัญหา) ในประวัติซ่อม เทียบได้กับ ISO 14224 taxonomy (plant/unit/system > equipment unit > subunit > maintainable item) และการบันทึก failure ที่ระดับ maintainable item/part; ให้ใช้ Smart Number ที่ระดับ Location และ Running Number ที่ระดับ Equipment; ไม่ฝังรหัสอะไหล่/บัญชี/แผนกในรหัสอุปกรณ์ (หนังสือไม่อ้าง ISO 14224 หรือ OREDA โดยตรงในช่วงหน้านี้)
- Failure data fields ใน WO (p.96, 109): Failure Mode, Object Part, Cause/Root Cause, Effect, Consequence, Effect Cost + Work Type, Down Time/Work Time/Wait Time, Resources (Man-Hrs, Stock, Non-stock, Outsource). เทียบกับฟิลด์ failure event ของ ISO 14224/OREDA (failure mode, failure cause/mechanism, failure effect, downtime, repair man-hours) — หนังสือไม่ได้ให้รายการรหัส Failure Mode/Cause ที่เป็นมาตรฐาน (ไม่มีตารางรหัสในช่วง p.89-112)
- กฎคุณภาพข้อมูล: ห้ามปิด CM-Unplanned WO ถ้ายังไม่ระบุ Failure Mode (เก็บเป็น Backlog-Failure Mode Undefined) (p.110-111, รูปที่ 4.16)
- RCM/FMECA: PM task ต้องผูกกับ Failure Mode และ Object Part (p.99-100); RAM process 2-4 (Criticality Assessment, Failure Consequences: Safety/Hidden/Operational/Non-Operational, Task Selection: Condition Monitoring/Part Replacement/Overhaul/Failure Finding, หรือ Run To Fail/Redesign) และ process 7 (FMECA) อยู่นอก CMMS (p.106-107); ความสัมพันธ์ CMMS-RCM รูปที่ 4.16 (p.110) — Foreground housekeeping vs Background RCM-FMECA/Optimization
- Criticality เป็นฟิลด์ใน Equipment Database -> Maintenance Strategy (p.96)
- Spares: Spare Part Database/Inventory Transaction, BOM, Min/Max/ROP/EOQ, Lead Time, Spare Optimization Recommendation, ขอบเขต Service Level vs Stock Level vs Plant Availability (p.100-103); ข้อมูล failure -> Spare Optimization (p.96)
- วิเคราะห์ที่ทำได้จากประวัติเสีย: Reliability/Probability of Failure, จำนวนครั้งคาดเกิด, คาบ PM เหมาะสม, ค่าใช้จ่ายคาดการณ์, Average Availability (p.111-112)
